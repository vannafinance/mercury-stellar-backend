1 · The system at a glance

A user states an objective in their own words. The system investigates the live account through audited reads, evaluates what is feasible, sizes it in deterministic code, proposes it for approval, executes leg by leg, and verifies what actually settled.

Six layers. Each one owns a decision the layer above it is not allowed to make.

The load-bearing rule: the model interprets language and chooses what to inspect. It never decides an amount, never decides what is safe, and never decides that something settled. What crosses from Layer 3 to Layer 4 is a validated shape — which operations, which assets, in what order — with no numbers in it. Every figure below that line is computed and re-derivable from its inputs.
Why the constraint is worth it. A model that cannot choose a number cannot invent one. Every serious bug this surface has produced looked identical from outside: the model said something plausible and wrong. Making arithmetic unreachable from the model removes the whole class rather than patching instances. This is not a limit on intelligence — understanding is deliberately unlimited; only arithmetic and authority are closed.

The steps, and why each exists

Step 1 — Domain classifier. One cheap Flash call, cached per prompt hash. Why: it replaced a 348-line regex blocklist that was written as a billing guard but also refused legitimate prompts because position\b did not match "positions". A model reads intent; a regex reads spelling.
Step 2 — Daily token cap, per verified subject. Why: this is what actually addresses cost. The regex firewall never did — it blocked shapes, not spend.
Step 3 — Fast path. Exact-match reads (price, health) answer in under a second and skip the loop. Why: a price question does not need an agent. Measured: 686ms through the fast path versus 38.7s when it fell through to the model. Critically this is a cache, not a fallback — it can only answer questions it matches exactly, and it can never override a researched plan.
Step 4 — Resolve scope (wallet bindings → margin account), cached five minutes, hard-capped at 20s. Why cached: two chained MCP calls run otherwise on every turn. Measured at 13.1s on a cold resolve — 81% of that turn. Why capped: it sits outside the loop's own deadline, so an unbounded stall here consumed the whole route budget.
Step 5 — Seed the position from the contract, 8s cap. Why from the contract: the app's snapshot is unbounded, shares a process-wide promise, and has been measured at 6.3s–96s. It caused five separate copilot failures. The contract read is one MCP call, cancellable, and reports the posted collateral the risk engine actually uses.
Step 6 — The loop decides what else to inspect. See §4.
Step 7 — Deterministic sizing and ranking. Integer WAD, no floats. Why integer: (1.3).toFixed(18) is 1.300000000000000044. That representation noise let a stated floor of exactly 1.1 slip past a threshold guard.
Step 8 — Drift guard. If the app snapshot and the contract disagree beyond max($0.50, 0.5%), refuse to quote a size. Why refuse rather than pick: consistency with a wrong figure does not prevent a liquidation. A dropped debt leg once showed HF 2.51 where the contract implied 1.56.

What the model can and cannot reach. 24 read capabilities are declared; zero write capabilities are. Identity — trader, smart account, holder — is bound from the verified session inside the resolver, never from model arguments. Arguments are validated against an exact key set, so an extra field cannot ride alongside legitimate ones. Amounts pass a strict decimal regex; assets must match an enum, and bare USDC is deliberately absent from it.

The measured gap, and why it exists

AppContractDifference
Collateral$1,087.20$953.80$133.40 — unposted SAC in the margin account
Debt$278.91$278.91agrees exactly — rules out timing
Health factor3.893.42solvency vs liquidation proximity
Both numbers are correct; they answer different questions. get_current_total_balance_internal walks only smart_account_contract_client.get_all_collateral_tokens() — posted collateral. The app additionally counts raw SAC balances held in the same margin account but never pledged. posted + unposted ÷ debt is a valid solvency measure; posted ÷ debt is liquidation proximity. Only the second one governs the 1.10 threshold, so the copilot quotes it for anything sizing-related and labels which it is using.

Facts that are not in doubt

  • The liquidation boundary is strictly greater than 1.10. Binary-searched against the deployed RiskEngine: is_account_healthy returns false at exactly 1.100000 and true at 1.100001. Measured, not assumed.
  • Borrowing raises both sides. The smart-account contract credits borrowed proceeds into its own collateral ledger, so a borrow of x adds x to gross assets and x to debt. Modelling it as debt-only once doubled real leverage silently.
  • A zero collateral row is not an empty position. Recorded BLEND_USDC can be 0 while the tracking balance is ~$120.
  • Zero balance with any non-zero debt is unhealthy — no dust tolerance.
  • "USDC" is not an asset. BLUSDC, AQUSDC and SOUSDC are three separate SACs. Bare USDC is deliberately absent from the enum handed to the model, so it cannot be chosen accidentally.

Why there is no editable amount field

An editable leg amount hands the user a control that can break the exact constraint the system exists to protect. Validation then fails, the card says "that breaks your 1.3 floor", and the user is reduced to guessing numbers against a solver. Edit the inputs — floor, budget, assets, borrow yes/no — never the output amounts. An expert who wants exactly 437 XLM still gets it, but the plan is relabelled user-sized rather than copilot-sized.

What requires proof of wallet ownership

ActionBinding?Why
Reads — positions, health, marketsNoPublic on-chain data. Anyone can read that address in a block explorer, so proof of ownership buys no confidentiality — it only blocks legitimate users.
Manual-signed writesNoThe user's own wallet signature is the proof.
Auto-signYesThe Sign Service signs on the user's behalf, so it must hold evidence they authorised that wallet.
Coupling all three to one mechanism caused four phases of misleading refusals. A binding is written only by a three-step consent flow reachable through enabling auto-sign. Connecting a wallet does not create one. So reads failed with "this wallet isn't linked to your signed-in account" while the Margin page rendered the same account perfectly — because it reads the chain directly and needs no binding at all.

Why execution lives in MCP, not the app

Not latency — writes are chain-bound anyway, so a 500ms hop is noise against settlement time. The reason is that transaction construction and spend policy must have exactly one implementation, server-side, where no caller can route around it. If the copilot built XDR itself and MCP built it too, the two would diverge on contract addresses, auth entries and caps. A cap enforced in the app is a cap you bypass by calling the API directly.

Why sessions are bound to user and client

Sessions were already bound to the verified assertion sub — a different identity could never spend them. That part was correct. What was missing was any distinction between our copilot and a third-party agent holding the same user's assertion: both got identical signing power. With MCP public, connecting any agent would have silently handed it the user's daily cap.

The governing property: capability degrades, it never escalates. A client with no grant receives the unsigned XDR — not a refusal, and not a signature. It can still do useful work; the user just signs it themselves in a first-party surface.
